# Architecture

## Data flow

1. `load_profile` parses controller settings and named physical channels.
2. `load_scenario` parses ordered test intent without protocol strings.
3. `compile_plan` resolves names, enforces pulse envelopes, and produces an
   immutable execution plan with a wire preview generated by `ssc32::Protocol`.
4. `run_plan` invokes `ssc32::Controller` only after explicit execution consent.
5. `RecordingTransport` decorates the real `ssc32::SerialTransport` and records
   the bytes that cross the transport boundary.
6. Evidence writers emit JSON and JUnit reports after success or failure.

The preview and execution use the same protocol library. The application does
not contain an independent SSC-32 command encoder.

## Boundaries

- **Profile:** physical wiring and permitted actuator envelope.
- **Scenario:** test intent using semantic channel names.
- **Plan:** validated, resolved, immutable commands and expectations.
- **Runner:** ordered execution and response assertions.
- **Evidence:** exact transport transcript and result record.

## Failure behavior

Configuration failures occur before the serial device is opened. Runtime
failure stops the plan and attempts an SSC-32 cancel command. The runner does
not issue an automatic return-to-home movement because a new movement after an
unknown failure can increase risk.

## Test strategy

- Unit tests cover parsing, name resolution, exact protocol preview, duplicate
  channels, and safety-envelope rejection.
- A pseudoterminal simulator exercises the real POSIX serial transport and the
  recording decorator without hardware.
- Physical execution remains a deliberate local action. Hosted CI never sends
  actuator commands.
